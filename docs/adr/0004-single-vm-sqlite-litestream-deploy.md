# Deploy as a single Fly.io VM with a volume, streamed by Litestream

GetTyping runs as one Fly.io VM with a persistent volume holding the SQLite file, and Litestream continuously streams that file to object storage for backup and disaster recovery. We picked this over a managed multi-writer database because nothing in the spec requires horizontal scale or multi-region writes, and the read-heavy Leaderboard workload is served from the same file a single writer already owns — the alternative is more moving parts for a scale this app doesn't have. The trade-off: the app can only ever run as many machines as can share one volume, which for SQLite is one. Migrations run explicitly on container start, before the app is exec'd, so a fresh or restored volume is always brought to schema before it can serve a request; the volume itself is never recreated or replaced by a deploy, which is precisely what keeps an in-flight Attempt handshake alive across a release (see `attempt_tokens` in [09-db-schema.md](../../.scratch/gettyping-spec/issues/09-db-schema.md)). If write volume or a genuine multi-region need ever shows up, **Turso** is the documented upgrade path — it speaks the same SQLite dialect and the drizzle schema carries over, but that migration is explicitly out of scope until the need is real.
