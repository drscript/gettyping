# GetTyping Build-Ready Spec

Label: wayfinder:map

## Destination

A build-ready spec for GetTyping: a web-based, SQLite-backed typing tutor covering two Tracks off a shared foundation — **Learn** (gated, stage-by-stage curriculum for beginners/kids 5+) and **Speed Test & Practice** (ungated diagnostic test + adaptively-generated exercises targeting weak keys). The spec must cover scope, user flows for both Tracks, the curriculum outline, the data model, Leaderboard rules, and visual/UX principles — ready to hand off to implementation without further open decisions.

- Decisions already recorded as ADRs: [0001 nickname-only identity](../../docs/adr/0001-nickname-only-identity.md), [0002 per-exercise leaderboards](../../docs/adr/0002-per-exercise-leaderboards.md), [0003 adaptive exercise generation](../../docs/adr/0003-adaptive-exercise-generation.md).
- Skills to consult per ticket: `/research` for research tickets, `/prototype` for prototype tickets, `/grilling` + `/domain-modeling` for grilling tickets.
- Standing preference: solo/indie project, no fixed timeline or budget, hosting choice folds into the tech-stack ticket.
- Foundational scope decisions (online multi-user web app, nickname-only identity, per-exercise Leaderboards, gated Learn track, ungated adaptive Speed Test & Practice track, baseline visual accessibility only, nickname safety/profanity filtering) were locked during destination-naming — see Destination above and the ADRs, not individual tickets.

## Decisions so far

- [Research SQLite concurrency & hosting patterns for a multi-user web app](issues/01-research-sqlite-hosting.md) — single VM + WAL SQLite + Litestream for backup/DR; Turso as the documented upgrade path if write volume or multi-region needs grow.
- [Research typing-pedagogy best practices for sequencing a beginner curriculum](issues/03-research-typing-pedagogy.md) — home row → top row → bottom row → punctuation → numbers; 1-3 new keys/stage; gate on ~90% accuracy not speed; 10-15 min stages for ages 5-7.
- [Choose tech stack: frontend framework, backend, hosting](issues/02-tech-stack.md) — Svelte + SvelteKit (adapter-node), Fly.io + Litestream, Drizzle ORM on better-sqlite3.
- [Design the Learn-track curriculum outline](issues/04-curriculum-outline.md) — 21 Stages (single unbranched sequence, one Exercise each), home→top→bottom row→shift→punctuation→numbers, flat 90% accuracy gate, cumulative recycled content.
- [Prototype weak-key detection & adaptive exercise generation logic](issues/05-prototype-weak-key-generation.md) — weakness score = errorRate×0.7 + latency×0.3 (3+ samples); both word-bank (readable default) and bigram (dense/unreadable) generation modes are valid, chosen by context; targeting-aggressiveness is a tunable 0-1 config value, not a locked constant; Weak-key Profile stores per (Player, key) attempts/errors/cumulative-latency.
- [Prototype the visual design for the typing interface](issues/06-prototype-visual-design.md) — one shared visual language flexed per Track (not two modes), on-screen keyboard on both Tracks, feedback pairs color with a glyph/shape (not color alone), Leaderboard hidden during the Attempt and revealed only on completing the Exercise.
- [Decide nickname uniqueness & identity persistence handling](issues/07-nickname-uniqueness.md) — Nicknames non-unique with no Leaderboard disambiguation and no recovery path; identity persists via a long-lived cookie holding an opaque Player UUID; Nicknames are editable post-creation but snapshotted onto each Score at Attempt time.
- [Define WPM/accuracy scoring formulas](issues/08-scoring-formulas.md) — Net WPM ranks Leaderboards, accuracy counts corrected errors, one formula for both Tracks, Score stores only aggregates (raw keystrokes discarded after feeding the Weak-key Profile).
- [Design the SQLite schema](issues/09-db-schema.md) — generated Practice Exercises are ephemeral (no Leaderboard, nullable `exercise_id` on Score for personal history); Leaderboards computed on read via window function, no materialized table; Weak-key Profile fed by both Tracks; Stages/Exercises are DB tables seeded via migration. Full `players`/`stages`/`exercises`/`scores`/`weak_key_stats` schema in the ticket, plus an addendum from the score-integrity ticket adding `attempt_tokens` and `scores.leaderboard_eligible`.
- [Decide Score computation & Leaderboard-integrity validation](issues/10-score-integrity.md) — posture is casual-tamper resistance (scripted clients accepted as out of reach); client POSTs raw keystroke events and the server derives every aggregate; Practice-Exercise generation moves server-side; an `attempt_tokens` start handshake gives a server-observed wall clock; structural failures reject, plausibility failures persist as `leaderboard_eligible = 0` (still counting for the Learn gate); Weak-key Profile fed by every accepted stream with latency clamped against interruption noise.
- [Design the first-run/onboarding flow](issues/11-first-run-onboarding.md) — Track choice → Nickname → typing on both Tracks; doors framed by intent (never age or self-assessed skill), backed by mis-pick recovery rather than a perfect router; Learn picks a Nickname from curated icon cards (safe by construction) while Speed Test types one; profanity checked on submit with a neutral redirect and no appeals path; a persistent "For grown-ups" route replaces any interstitial; returning Players land on a light home screen; the identity cookie becomes `{ active, players[] }` so siblings on one device don't blend Weak-key Profiles (amends [07](issues/07-nickname-uniqueness.md), no schema change).
- [Decide whether GetTyping has audio, and what it covers](issues/12-audio-design.md) — audio is in, narrow and always silenceable: error-only keystroke ticks (soft, non-escalating, self-attenuating as accuracy improves) plus rare event moments; no music, no spoken prompts, no per-Track flex. Hard invariant: every sound is strictly redundant with the visual channel, so muting is lossless and autoplay blocking is a non-event. Audio is reinforcement for a *sighted* Player whose eyes are on their hands — explicitly not assistive tech; the accessibility line is unmoved. Defaults on, single toggle reachable mid-Attempt, preference stored **device-scoped** in the cookie (mute is a property of the room, not the person) — no schema change.
- [Design the Learn-track gate-failure and retry flow](issues/13-gate-failure-flow.md) — a missed gate goes to a distinct failure state with **no Leaderboard** (refines [06](issues/06-prototype-visual-design.md): revealed on *clearing*, not merely finishing); retries replay identical text, making explicit the rule **fixed content ⟺ has a Leaderboard, generated content ⟺ none**; no escalating hints because 06's next-key keyboard is already permanently on; a stuck Player is freed by an **adult-granted override** via the grown-ups route, never a child-facing skip and never a lowered bar (needs a new `stage_unlocks` table — addendum on [09](issues/09-db-schema.md)); no failure sound, since it would fire loudest for the child struggling most; and Learn Leaderboards now require a gate-clearing Score, as a query predicate rather than by overloading `leaderboard_eligible`.
- [Design the Speed Test & Practice session loop](issues/14-practice-loop.md) — the Speed Test is a one-time **prerequisite** for Practice (sequencing, not a pass/fail gate); its result screen carries a dominant "practise your weak keys" CTA beside 11's conditional route-to-Learn offer; practice is **Player-paced** (compact stats between Exercises, "next" dominant, "finish" subordinate) and ends in a **session summary showing the Weak-key Profile shifting** — the first surface that ever shows a Player the adaptive targeting working; the Profile becomes **recency-weighted** (counters decay on write) because lifetime totals meant a Player who had fixed a key kept being served it (amends [05](issues/05-prototype-weak-key-generation.md), no schema change), making a Speed Test retake an ordinary Attempt; and the Track keeps exactly **one Leaderboard** — the Speed Test's, which is the app's de facto flagship board and therefore has **immutable content** (a new text needs a new Exercise row, never an edit).

- [Settle the Leaderboard display rules](issues/15-leaderboard-display-rules.md) — ties break on `id ASC` in **both** query clauses, fixing a live nondeterminism defect (boards could reshuffle between reads) and stopping a renamed Player's row flickering between snapshotted Nicknames; a Player outside the top 10 gets their own row appended with their true rank plus a **personal-best marker**, which is the part that motivates a beginner at #47; an ineligible Score appears on that row **marked unranked with no explanation** (mirroring 11's profanity redirect — state the outcome, never name the detection); and the board is **suppressed entirely below a threshold of distinct ranked Players**, since a two-row board manufactures a competitive signal that doesn't exist — below it the reveal shows the personal panel alone, so stats survive suppression and one component serves both contexts. Addenda on [09](issues/09-db-schema.md) (tie-break plus two previously-unnamed reads) and [06](issues/06-prototype-visual-design.md) (reveal now conditional twice over).

- [Design Learn-track completion and Stage revisiting](issues/16-learn-completion-and-revisiting.md) — cleared Stages are **freely replayable** (which is what [09](issues/09-db-schema.md)'s best-Score window function always assumed, and what makes [15](issues/15-leaderboard-display-rules.md)'s personal-best marker able to move at all), reached via a **Stage list on the home screen** rather than a second navigational surface; every Attempt persists, worse ones included, because *recorded* and *ranked* were already separate concepts; a sub-gate replay of a cleared Stage is **not a failure** — the Leaderboard reveal is now keyed to *the Stage being cleared*, by this Attempt or any earlier one (refines [13](issues/13-gate-failure-flow.md)); Stage 21 ends on a **distinct completion screen whose dominant CTA is the Speed Test**, mirroring [14](issues/14-practice-loop.md)'s hand-off into Practice, after which [11](issues/11-first-run-onboarding.md)'s existing "next unlocked Stage, *or the Speed Test*" rule covers graduates with no new rule; and `stage_unlocks` is **re-read as "Stage *n* is resolved"** rather than "Stage *n+1* is available", so an adult override works on the final Stage without a dangling Stage 22 — same table, same columns. Addenda on [09](issues/09-db-schema.md), [13](issues/13-gate-failure-flow.md), [11](issues/11-first-run-onboarding.md) and [06](issues/06-prototype-visual-design.md).

- [Decide whether a Player can see their own history, and what it shows](issues/17-personal-history-surface.md) — six tickets justified retaining Scores by appealing to "personal history" and [09](issues/09-db-schema.md) carried a **dedicated index plus a nullable `exercise_id`** for it, while no ticket ever specified the surface; **it exists**, as a plainly-styled route off the home screen (the hub-with-routes pattern [11](issues/11-first-run-onboarding.md) built, not the extra entry point 11 and [16](issues/16-learn-completion-and-revisiting.md) refused — and not adult-gated, since a Player's own Scores are not an adult's business). It is **sectioned by what each Track can honestly say**: a Speed Test WPM trend, which is the app's only apples-to-apples series and only because [14](issues/14-practice-loop.md) froze that text; Learn bests per cleared Stage; and Practice as an **aggregate plus the current Weak-key Profile, never individual generated Attempts**, since each targeted different keys and listing them renders noise as data. An ineligible Score is **listed with [15](issues/15-leaderboard-display-rules.md)'s existing "not ranked" marker but excluded from the trend** — marked where it is a row, absent where it would be a claim. The momentary surfaces (15's personal row, 14's session summary, 16's Stage list) were judged insufficient because none answers "am I better than a month ago", which is the Speed Test Track's whole proposition. **No schema change** — 09's index and nullable FK stop being speculative. Addenda on [09](issues/09-db-schema.md), [11](issues/11-first-run-onboarding.md), [15](issues/15-leaderboard-display-rules.md) and [06](issues/06-prototype-visual-design.md).

## Not yet specified

- Which contexts within Speed Test & Practice call for word-bank vs. bigram-mode generation, and the production-tuned default value for the targeting-aggressiveness knob — genuinely needs live playtest data (see [weak-key generation prototype](issues/05-prototype-weak-key-generation.md)), not yet sharp enough to ticket.
- The Speed Test score floor below which the app offers "start from the beginning instead?" — same shape as the targeting-aggressiveness knob: a playtest-tuned number, not a spec constant (see [Design the first-run/onboarding flow](issues/11-first-run-onboarding.md)).
- How many consecutive failures on a Stage before the failure screen surfaces the adult-override line — the third playtest-tuned number of the same shape (see [Design the Learn-track gate-failure and retry flow](issues/13-gate-failure-flow.md)).
- The Weak-key Profile's decay factor — how fast old samples lose weight. The fourth playtest-tuned number: too slow and the Profile stays stale, too fast and it chases noise (see [Design the Speed Test & Practice session loop](issues/14-practice-loop.md)).
- The minimum number of distinct ranked Players before an Exercise's Leaderboard is displayed at all — the fifth, and the one most dependent on real traffic rather than playtesting (see [Settle the Leaderboard display rules](issues/15-leaderboard-display-rules.md)).

## Out of scope

- Exact stage-by-stage lesson content/copy (specific text/word lists per Stage) — the destination requires the curriculum *outline* (Stage count, keys, order, thresholds — settled in [Design the Learn-track curriculum outline](issues/04-curriculum-outline.md)), not fully-authored lesson text; writing the actual words/sentences per Stage is content-authoring work for implementation time, not a spec decision.
- Exact word-bank/bigram content authoring for Speed Test & Practice generation (the literal word lists and synthesis vocabulary) — like the Learn track's lesson copy, this is content-authoring work for implementation time; the generation *approach* (scoring formula, dual-mode strategy, config shape) is settled in [Prototype weak-key detection & adaptive exercise generation logic](issues/05-prototype-weak-key-generation.md).
- The curated word list backing generated Nickname candidates (the literal words and their icons) — same category as Stage lesson copy and word-bank vocabulary: content-authoring for implementation time. The *mechanism* — a curated list that makes picked Nicknames safe by construction, leaving the profanity filter to run on free text only — is settled in [Design the first-run/onboarding flow](issues/11-first-run-onboarding.md).
- Multi-Player profile management beyond a "Not you?" switch (removing Players, avatars, a picker on every load) — ruled out in the same ticket: the cookie's `{ active, players[] }` list plus one switch affordance solves the shared-family-device problem, and anything richer is scope creep into the account system this app has deliberately refused to build.
- The audio assets themselves (the actual sound files and their character) — content-authoring for implementation time, same category as Stage lesson copy, word banks, and the Nickname word list. The *constraints* on them (soft, short, non-escalating, strictly redundant with the visual channel) are settled in [Decide whether GetTyping has audio, and what it covers](issues/12-audio-design.md).
- Background music and spoken prompts/voice narration — ruled out in the same ticket: music works against 06's focus principle and is the first thing a parent mutes, and voice's pedagogical rationale (Read, Write & Type's phonics integration) was attached to a curriculum model [04](issues/04-curriculum-outline.md) declined, while recorded speech collides with the out-of-scope i18n line.
- Native mobile apps — this is a web-based build; app-store packaging isn't.
- Real-time multiplayer typing races — Leaderboards give the competitive hook without live-race infrastructure.
- Monetization/ads.
- Non-English content and non-QWERTY keyboard layouts.
- UI localization/i18n.
- Screen-reader/full assistive-tech support — baseline visual accessibility only (colorblind-safe feedback, legible sizing/contrast), decided during destination-naming.
- Admin/moderation tooling for removing a bogus Leaderboard entry — ruled out in [Decide Score computation & Leaderboard-integrity validation](issues/10-score-integrity.md): the `leaderboard_eligible` column is the lever and manual SQL against the VM's SQLite file is the intended, sufficient interface. An admin surface would introduce the only credential in an app that has refused authentication everywhere else, for the rarest event in the spec.
- Behavioural anti-cheat (keystroke-rhythm fingerprinting, timing-distribution analysis) — ruled out by the casual-tamper-resistance posture in the same ticket; disproportionate for a solo project and carries real false-positive risk against genuinely fast typists.
- Deployment/CI pipeline specifics (build/test/deploy workflow, Litestream restore drills, etc.) — the destination's required spec content is scope, user flows, curriculum, data model, Leaderboard rules, and visual/UX principles; the platform choice itself (Fly.io) is settled in [02-tech-stack.md](issues/02-tech-stack.md), but the operational pipeline is implementation-time work, not spec content.
